# Архитектура игровых проектов и паттерны кода геймплея

Как устроить код игры, чтобы правила можно было тестировать, гонять ботами тысячи партий, воспроизводить баги и править контент без программиста. Справочник движко- и языко-независимый. Реализация на конкретном языке и движке — в скиллах rust-knowledge и gdscript-knowledge, если они установлены.

## 1. Главные инварианты

1. **Правила отдельно от представления.** Ядро правил не зависит от движка, сети и IO. Оно выдаёт события и запросы выбора, клиент их проигрывает. MTG Arena разделяет GRE (правила) и Duel Scene (клиент); в Legends of Runeterra клиент и сервер на C#, а логика карт вынесена в Python-скрипты.
2. **Ядро не знает конкретных карт.** GRE знает приоритет, фазы и шаги, но «не знает, что делает каждая из тысяч карт»: карты — независимые правила, которые правят список доступных действий. В argentum-engine «no card-specific logic» в движке, карты — данные на DSL. Так же устроены Fireplace, Forge и LoR.
3. **Порядок разрешения задают явные структуры, а не порядок вызовов функций.** Очередь действий (Slay the Spire), стек с приоритетом (MTG), фазы и очереди триггеров, неизменяемые после начала разрешения (Hearthstone по реверс-инжинирингу сообщества). Плюс цикл state-based проверок «до стабилизации» и слои непрерывных эффектов (MTG CR 613).
4. **Детерминизм — инструмент разработки, а не только сетевая техника.** У Riot детерминизм LoL начался как средство повторяемых тестов по записанному вводу (Delta Checker), потом из него вырос Chronobreak. Реплеи Overwatch служат и kill cam, и воспроизведению багов. Для пошаговой игры хватает seed + лога команд.
5. **Тесты геймплея — это сценарии.** Регрессионный тест GRE — «маленькая скриптовая партия Magic». В XMage около 9000 юнит-тестов и тест-режим заданных позиций. Riot BVS гоняет около 5500 функциональных тестов на сборку.
6. **Data-driven значит «контент правят без программиста».** У Bilas (Dungeon Siege) буквально «No engineer required». Таблицы со схемой и валидатором, слои контента и окружения на ветку (LoR) превращают балансную правку в правку данных.

## 2. Симптом, паттерн, источник

Таблица «Симптом → паттерн → источник» — вход для этапа 10 [пайплайна](pipeline.md#этап-10-поиск-в-библиотеке-знаний), когда проблема в коде, а не в дизайне. Номера П ведут в [каталог](#3-каталог-паттернов). Найденное решение оформляется карточкой гипотезы с типом «правило» или «данные».

| Симптом | Паттерн | Источник |
| --- | --- | --- |
| Эффекты карт ломают друг друга, результат зависит от порядка вызовов | Очередь действий (П14) или стек (П15) + очереди триггеров (П16) + слои (П19) | BaseMod/StS; MTG CR; Hearthstone Advanced rulebook |
| В ядре правил растут `if card.id == ...` | Whiteboard (П17), правила как данные (П22) | Werner 2023 (GRE); Forge; Fireplace |
| Аура или бафф дают разный результат в зависимости от порядка розыгрыша | Пересчёт производных характеристик по слоям и таймстемпам + dirty flag (П19) | MTG CR 613; SabberStone «onion» |
| Существо «умирает» посреди эффекта и ломает следующий шаг | Отложенные state-based проверки после внешней фазы (П20) | Hearthstone Advanced rulebook; phase-rs |
| «Вместо этого…» и «предотвратите…» сделаны хаками | Proposed event + цепочка замен (П18) | MTG CR; Forge `R:` |
| Баг не воспроизводится, тестер не может описать шаги | Seed в состоянии + лог команд = реплей (П25) | Riot Determinism 2017; Orwig 2017 |
| Две одинаковые прогонки симулятора дают разные метрики | Аудит источников недетерминизма (П25), реплеи как регрессия (П43) | Fiedler; Riot 2017 |
| Клиенты разошлись, «out of sync» через 10 минут | Чексуммы состояния каждый ход (П26); лог состояния и diff до первого расхождения | 1500 Archers; Fiedler; Hoskinson 2018 |
| Читер видит руку соперника | Авторитарный сервер + фильтр видимости (П28) | Gambetta; XMage |
| Бот «знает» скрытые карты, метрики баланса завышены для бота | Бот получает только `view` + детерминизацию (П40) | Cowling et al. 2012 |
| Симулятор медленный, замер этапа 8 идёт часами | Чистое ядро без движка (П21, П23), дешёвое копирование состояния, бенчмарки горячих путей (раздел 5) | Schwab 2014; phase-rs |
| MCTS-бот невозможен: копия состояния дорогая или ломает глобальные данные | Неизменяемое состояние, редьюсер (П21) | phase-rs; argentum-engine |
| Логику правил нельзя запустить без движка или редактора | Отделение правил от представления (П23), модуль `rules-core` (раздел 4) | GRE ↔ Duel Scene; argentum-engine |
| Анимация «ждёт» и ломает порядок логики | Ядро выдаёт поток событий, клиент проигрывает их асинхронно (П23) | GRE ↔ Duel Scene |
| Выбор цели или X посреди эффекта блокирует логику на UI | Запрос решения как состояние ядра (П24) | Werner 2023 |
| Нужен undo (пазлы, обучение) или «что если» для ИИ | Command + неизменяемое состояние (П11, П21) | Nystrom: Command; phase-rs |
| Дизайнер ждёт программиста ради правки чисел | Таблицы со схемой (П32) + горячая перезагрузка (П33) | Bilas 2002; CastleDB; Hipple 2017 |
| Дизайнер ждёт программиста ради новой механики карты | DSL или скрипт на карту (П22) | LoR 2021; Fireplace |
| Опечатка в данных карты всплывает крашем в рантайме | Валидатор схемы в CI (П32) | CastleDB; LoR RGDS |
| Баланс правят в Google Sheets, а в репозитории и на сервере другие числа | Таблица — единственный источник истины, импорт через API с валидацией, снимок импорта по хешу (П32) | Hallett 2021 (Hutch) |
| Текст карты расходится с реальным эффектом | Текст генерируется из данных эффекта + шаблоны Fluent (П36) | Project Fluent |
| Невыпущенные карты утекают в билд | Слои контента, флаги публикации (П35) | Glegg 2019 |
| Регрессии ядра находят игроки | Сценарные тесты (П42) + корпус реплеев (П43) в CI | Werner 2023; XMage; Riot |
| E2E-тесты нестабильны | Условные ожидания, линейные тесты, карантин (П44) | Merrill 2016 |
| Дисбаланс карты обнаружен после релиза | Массовые симуляции ботами + телеметрия (П45) | Schwab 2014; Giovannetti 2019 |
| После патча старые сейвы или реплеи не грузятся | Версия схемы + миграции, версия правил в реплее (П31) | Factorio: Migrations; Unreal `FCustomVersion` |
| Случайный бот нашёл краш, но последовательность из 300 ходов не разобрать | Stateful property-based тест: генератор команд, инварианты после шага, shrinking (П45) | Hypothesis stateful; proptest-state-machine |
| Синглтоны везде, связи между системами скрыты | Явная передача зависимостей (П13), данные и события как ассеты (П7) | Nystrom; Hipple 2017 |
| Звук и UI дёргаются синхронно из логики, дубли звуков | Event Queue с агрегацией (П12) | Nystrom: Event Queue |
| Модальный выбор не возвращает прежнее состояние | Pushdown automaton (П10) | Nystrom: State |
| Набор булевых флагов даёт невалидные комбинации | FSM, параллельные и иерархические машины (П8, П9) | Nystrom: State |
| Иерархия классов юнитов превратилась в «blob» | Компоненты или ECS (П3, П4) | West 2007; Bilas 2002; ECS FAQ |
| FSM врага разрослась до n² переходов | BT или HTN (П37, П39) | Isla 2005; Humphreys (GAP1) |
| ИИ-агент «дёргается» между решениями | Utility с инерцией (П38) | Mark & Dill 2010 |
| Физика и логика зависят от FPS | Фиксированный шаг + интерполяция (П1) | Fiedler 2004 |
| «Тормозит», но непонятно где | Бюджет кадра + профайлер в dev-сборках (П46) | Gyrling 2015; Tracy |
| Универсальная система эффектов придумана заранее и мешает | Компрессия: абстракции после повторов (П34) | Muratori 2014 |

## 3. Каталог паттернов

Формат строки: проблема → решение; когда не применять; источник. Полные ссылки — в [разделе 7](#7-источники).

### 3.1 Цикл и время

| № | Паттерн | Проблема → решение | Не применять | Источник |
| --- | --- | --- | --- | --- |
| П1 | Фиксированный шаг + интерполяция | Логика зависит от FPS → аккумулятор времени, симуляция целыми шагами dt, рендер интерполирует (`alpha = acc/dt`), число шагов за кадр ограничено против «spiral of death» | В пошаговой ККИ логика событийная; шаг нужен только анимациям и таймерам | Fiedler 2004; Nystrom: Game Loop |
| П2 | Явный порядок систем по фазам кадра | Неявный порядок обновления, баги «на один кадр» → фазы ввод → логика → физика → презентация, зависимости закреплены | Для правил ККИ: порядок задаёт очередь или стек, а не кадр | Nystrom: Update Method; West 2007 |

### 3.2 Объектная модель

| № | Паттерн | Проблема → решение | Не применять | Источник |
| --- | --- | --- | --- | --- |
| П3 | Компоненты вместо наследования | Иерархия разрастается в «blob», дизайнер просит гибрид веток → сущность из независимых компонентов; переход постепенный, через «blob-компонент» | 5–10 типов объектов без комбинаторики | Bilas 2002; West 2007; Nystrom: Component |
| П4 | ECS | Тысячи однотипных объектов, запросы «все X с Y без Z» → сущность = ID, компонент = данные, система = логика; архетипы или sparse set | Мало сложных сущностей с глубокой логикой (рука, стек). Свой ECS ради скорости обычно не окупается | Martin 2007; ECS FAQ; Ford, GDC 2017 |
| П5 | Type Object | Карта = класс, дизайнер не добавит карту без кода → `CardDef` (неизменяемые данные) и `CardInstance` (id, владелец, зона, модификаторы, ссылка на def) | Десяток карт, все уникальны по механике | Nystrom: Type Object |
| П6 | Сущность как словарь тегов | Эффекты меняют произвольные атрибуты → набор `GameTag → int`, любое изменение сериализуется и диффится | Полей мало и важна статическая типизация; теги размывают инварианты, нужна валидация | Hearthstone Internal design (теги восстановлены сообществом из клиента, это не исходный код Blizzard) |
| П7 | Данные и события как ассеты | Синглтоны и жёсткие ссылки между сценами → переменные, события и runtime-наборы как ресурсы-данные | Логика правил со строгим порядком: глобальные события скрывают последовательность | Hipple, Unite 2017 |

### 3.3 Поведение и состояния

| № | Паттерн | Проблема → решение | Не применять | Источник |
| --- | --- | --- | --- | --- |
| П8 | FSM, параллельные машины | Булевы флаги дают невалидные комбинации → enum-состояние; независимые аспекты в разных машинах, чтобы состояния складывались, а не перемножались | Сложный ИИ: там BT, utility или планировщик | Nystrom: State |
| П9 | Иерархические машины, statecharts | Одинаковые переходы во многих состояниях (фазы хода, UI-флоу) → суперсостояния, параллельные регионы | 3–4 состояния | Nystrom: State; statecharts.dev; Isla 2005 |
| П10 | Pushdown automaton | Модальный выбор («выберите карту для сброса») должен вернуть прежнее состояние → стек состояний | Возврат всегда в одно состояние | Nystrom: State |
| П11 | Command | Ввод, ИИ и сеть меняют состояние разными путями → любое намерение — сериализуемая команда (`PlayCard{card_id, targets}`); ИИ генерирует те же команды. Nystrom: «It takes discipline to make sure every data modification goes through a command» | Одноразовые действия без undo, ремапа и сети | Nystrom: Command |
| П12 | Observer, Event Queue | Звук, UI, достижения жёстко связаны с логикой → Observer развязывает получателя, очередь — время. Событие несёт все данные; не слать события из обработчика | Отправителю нужен ответ. Глобальная шина — это глобальная переменная | Nystrom: Observer, Event Queue |
| П13 | Service Locator (осторожно) | Глобальный доступ к аудио и логгеру → реестр с null-объектом | Для RNG и состояния в коде правил: их передавать явно, иначе ломается детерминизм | Nystrom: Service Locator |

### 3.4 Движок правил карточных и пошаговых игр

| № | Паттерн | Проблема → решение | Не применять | Источник |
| --- | --- | --- | --- | --- |
| П14 | Очередь действий | Эффект из нескольких шагов, реакции вклиниваются, прямые вызовы дают неверный порядок → `use()` карты только ставит атомарные действия в очередь: `addToBottom()` обычно, `addToTop()` для немедленной реакции; между действиями можно анимировать | Нужен ответ противника с приоритетом: тогда стек | BaseMod wiki (Slay the Spire) |
| П15 | Стек + приоритет | Игроки отвечают друг другу → стек объектов, ждущих разрешения; приоритет по кругу; все пасуют — разрешается верх | Нет инстант-ответов. Дорого по UX: Arena и Runeterra много вкладывают в автопас | MTG CR; phase-rs, Forge, XMage |
| П16 | Фазы и очереди триггеров | Триггеры одного события в случайном порядке, новые сущности вмешиваются → событие открывает фазу, подписчики собираются в очередь в порядке ввода в игру; очередь неизменяема после начала разрешения; смерти — после внешней фазы | Игрок сам упорядочивает свои триггеры (MTG): нужен выбор порядка и стек | Hearthstone Advanced rulebook |
| П17 | Whiteboard | Сотни карт меняют общие проверки («нельзя разыграть», «стоит на 1 меньше») → ядро строит предложенный список действий, независимые правила карт его правят, ядро исполняет итог. Взаимодействия возникают без парных спецслучаев | Меньше примерно 50 карт и редкие взаимодействия: простые хуки дешевле | Werner 2023 |
| П18 | Замены и предотвращение | «Если умрёт — вместо этого изгони» → событие создаётся как proposed, применимые замены переписывают его (каждая не более раза), потом исполнение; порядок замен выбирает затронутый игрок | Только триггеры «после». Не смешивать замены и триггеры в одном механизме | MTG CR 614 (614.5: замена не применяется повторно), 616 (порядок выбирает затронутый); Forge `R:`; Werner 2023 |
| П19 | Слои непрерывных эффектов | Ауры, смена контроля, копирование, «теряет способности» зависят от порядка наложения → базу не мутировать; производное = база + упорядоченные эффекты (слои, внутри слоя таймстемп и зависимости); пересчёт по dirty flag | Только аддитивные модификаторы: хватит суммы (onion SabberStone) | MTG CR 613; Magic Judges; SabberStone; Nystrom: Dirty Flag |
| П20 | State-based проверки до стабилизации | Смерть при 0, лимиты зон проверяются в каждом эффекте → после разрешения элемента или внешней фазы гонять глобальные проверки, пока что-то меняется; потом приоритет | Внутри разрешения одного эффекта: Hearthstone не проверяет смерть посреди события | phase-rs; Hearthstone Advanced rulebook; MTG CR |
| П21 | Чистый редьюсер | Мутации размазаны, нет undo и «что если» → `apply(state, action) → (state', events)` над неизменяемым состоянием (персистентные структуры); форк для ИИ дешёвый | Реалтайм с десятками тысяч объектов: там DOD и мутация на месте; допустим гибрид | phase-rs; argentum-engine; Carmack 2012 |
| П22 | Правила как данные, DSL эффектов | Каждая карта требует программиста, баги повторяются → карта из примитивов (`Hit(target, n)`, `Buff`, `Draw`, селекторы, `EVENT.on(...)`), escape hatch на скрипте для уникальных, подсказки ИИ в данных карты | Механик меньше 10–15 и они ещё меняются: DSL цементирует ошибки (П34) | Fireplace; Forge; LoR 2021; GRE + GRP; argentum-engine |
| П23 | Отделение правил от представления | Анимации и UI вмешиваются в логику, нельзя гонять headless → ядро без движка и сервера выдаёт события и запросы выбора, клиент их проигрывает, анимации не блокируют логику | Почти всегда применять; исключение — прототип на вечер | Werner 2023; argentum `rules-engine`; Glegg 2019 |
| П24 | Запрос решения | Выбор посреди разрешения блокирует логику на UI → ядро стоит в состоянии «ждём решение игрока P: варианты, ограничения»; человек, бот и тест отвечают одной командой | Не бывает: нужен любым эффектам с выбором | Werner 2023; GGRS (запросы вместо колбэков) |

### 3.5 Детерминизм, реплеи, сеть, сохранения

| № | Паттерн | Проблема → решение | Не применять | Источник |
| --- | --- | --- | --- | --- |
| П25 | Seed + лог команд = реплей | Баг не воспроизводится → один RNG в состоянии, seed записан; нет итерации хеш-коллекций с недетерминированным порядком, системного времени, неконтролируемого float. Реплей прикладывается к баг-репорту и становится тестом | Игра целиком на недетерминированной физике движка: тогда снапшоты | Hoskinson 2017; Orwig 2017; Fiedler 2014 |
| П26 | Чексуммы состояния | Клиенты тихо разошлись → хеш значимого состояния каждый ход сверяется, при расхождении сохранить оба состояния. Хеш говорит «где-то разошлось», но не где: Riot вместо чексумм пишет лог состояния ключ-значение (только изменения) и скриптом ищет первое расхождение двух прогонов | Чисто авторитарный сервер без клиентской симуляции | 1500 Archers; Hoskinson 2018 |
| П27 | Deterministic lockstep | Состояние слишком велико для пересылки (RTS) → пересылаются команды с исполнением через N ходов | Скрытая информация: у каждого клиента полное состояние, рука соперника открыта. Отзывчивый реалтайм с высоким RTT | 1500 Archers; Fiedler 2010, 2014 |
| П28 | Авторитарный сервер + фильтр видимости | Клиент с полным состоянием — готовый чит → сервер держит состояние и RNG, клиенту уходит `view`; карта раскрывается событием; id скрытых карт перемешиваются при уходе в скрытую зону [не проверено: общая практика] | P2P с полной информацией (шахматы) | Gambetta; XMage; Cockatrice |
| П29 | Клиентское предсказание + сверка | Ожидание сервера ощущается лагом → клиент применяет ввод сразу, при ответе откатывается и переигрывает неподтверждённое | Пошаговая ККИ с исходом от скрытой информации или RNG: хватит мгновенной анимации намерения | Gambetta, Part II; Fiedler 2010 |
| П30 | Rollback | Файтинг в P2P, задержка ввода недопустима → предсказать ввод, при расхождении загрузить снапшот и пересимулировать (до 8 кадров за 16 мс у NetherRealm) | Пошаговые игры; тяжёлое состояние без дешёвого снапшота | GGPO; GGRS; Stallone 2018 |
| П31 | Версионируемые сохранения | Патч ломает старые сейвы и реплеи → `schema_version`, цепочка миграций, тесты на «золотых» старых сейвах; в реплее версия правил и контента; хранить данные, а не ссылки на код. В Factorio миграции — файлы в папке `migrations`: сначала JSON-переименования прототипов, потом Lua-скрипты над загруженным состоянием; сейв помнит по имени, какие миграции уже применены. В Unreal версия ведётся на подсистему: `FCustomVersion` = GUID + целое, слишком старый пакет можно отклонить валидатором | Джем-прототип | Factorio: Migrations; Unreal `FCustomVersion`; Fowler, Event Sourcing. Доклада GDC по теме не найдено |

### 3.8 Тестирование и производительность

| № | Паттерн | Проблема → решение | Не применять | Источник |
| --- | --- | --- | --- | --- |
| П42 | Сценарные тесты («маленькая партия») | Карта работает одна и ломается в комбинации → сценарий «дано: у P1 в руке X, на столе Y; когда: разыграть X в Z; тогда: …», каждый баг-фикс добавляет сценарий, headless в CI | Не бывает: основа QA движка правил | Werner 2023; XMage; argentum `e2e-scenarios` |

| П45 | Массовая симуляция | Дисбаланс и краш-комбинации находят после релиза → боты играют тысячи партий headless, телеметрия и проверка инвариантов; случайные законные ходы работают как фаззинг правил. Удобная форма — stateful property-based тест: генератор выбирает законные команды, инварианты (число карт по зонам сохраняется, после SBA нет существ с нулём здоровья, `view` без чужих `def_id`) проверяются после каждого шага, упавшая последовательность ужимается (shrinking) до короткой и становится сценарием П42 | Замена живого плейтеста «по ощущению» | Schwab 2014; Giovannetti 2019; Hypothesis stateful, proptest-state-machine (игрового первоисточника нет) |
| П46 | Бюджет кадра и постоянная телеметрия | «Тормозит», непонятно где → бюджет 16.6 или 33.3 мс по подсистемам, инструментальный профайлер в dev-сборках, дешёвый постоянный metering | Микрооптимизация до измерений | Gyrling 2015; Tracy; 1500 Archers; Acton 2014 |
| П47 | Функциональное ядро, императивная оболочка | Скрытые зависимости от состояния → логика — чистые функции от явных входов, мутации в одном месте | Горячие циклы на миллионах элементов, где копирование дорого | Carmack 2012, 2007 |

Предостережения. Строгий ECS (Overwatch, Bevy) для пошаговой ККИ чаще избыточен: важнее чистое ядро и очередь или стек, а ECS полезен презентационному слою и реалтайм-жанрам. Rollback и предсказание пошаговым играм не нужны, lockstep несовместим со скрытой информацией.

## 4. Как устроить движок правил карточной игры

Синтез из GRE (Werner 2023), Hearthstone Advanced rulebook, StS/BaseMod, Forge, XMage, phase-rs, argentum-engine, Fireplace, LoR и MTG CR. Это рекомендация, а не устройство одной конкретной игры.

### 4.1 Слои и направление зависимостей

```text
content: определения карт (данные + DSL эффектов + подсказки ИИ)   ← валидатор схемы в CI
   │
rules-core (без движка, сети, IO):
   GameState (неизменяемый или версионируемый), RNG(seed) внутри состояния
   Command → apply(state, cmd) → (state', [Event], DecisionRequest?)
   ├─ цикл: очередь/стек → разрешение → SBA до стабилизации → триггеры → приоритет
   ├─ непрерывные эффекты: derive(state) по слоям и таймстемпам
   ├─ замены: ProposedEvent → правки → исполнение
   └─ DecisionRequest: ждём выбор от игрока, бота или теста
   │
ai: зависит только от rules-core
server: полное состояние, лог команд, фильтр видимости
client: проигрывает [Event] анимациями, рисует DecisionRequest
tools: редактор и валидатор карт, проигрыватель реплеев, массовый симулятор
tests: сценарии «маленькая партия», корпус реплеев
```

Зависимости направлены внутрь, к `rules-core`. Так устроены argentum-engine (`rules-engine`, `game-server`, `gym`, `e2e-scenarios`) и phase-rs (ядро → WASM, клиент React, сервер WebSocket). Даже в прототипе на неделю `rules-core` без движка окупается почти сразу: на нём держатся тесты, боты и симулятор этапа 7.

### 4.2 Решения по шагам

1. **Состояние.** Одна сериализуемая структура `GameState`: зоны (упорядоченные списки id), экземпляры карт (`id, def_id, owner, controller, zone, base, counters, tags, timestamp`), очередь или стек, фаза и шаг, приоритет, RNG, счётчик таймстемпов, история партии для запросов вроде «сколько заклинаний сыграно» (как History в LoR).
2. **Только команды меняют состояние.** Игрок, бот, тест и сеть подают одинаковые `Command`. Нелегальная команда отвергается до применения (в Age of Empires команды проверялись при отправке и при получении).
3. **Атомарные действия.** Эффект карты не меняет состояние напрямую, а порождает примитивы (`Damage`, `MoveZone`, `Draw`, `AddCounter`, `CreateToken`), которые идут через общий конвейер.
4. **Выбор структуры порядка.** Нужны ответы противника — стек + приоритет. Не нужны — очередь с `top/bottom` (StS) или фазы с очередями триггеров (Hearthstone). Триггеры одного события упорядочиваются детерминированно (порядок ввода в игру, таймстемп или APNAP), очередь фиксируется при начале разрешения.
5. **Конвейер одного примитива:** `Proposed` → замены и предотвращение (каждая не более раза) → исполнение → `Event` в лог → сбор триггеров «после» → после внешней фазы пересчёт непрерывных эффектов → SBA до стабилизации → постановка триггеров → приоритет.
6. **Непрерывные эффекты.** База не мутируется. `derive(state)` упорядочивает эффекты по слоям и таймстемпам и кешируется по dirty flag. При только аддитивных механиках хватает onion-стека модификаторов.
7. **Модификаторы правил (whiteboard).** «Можно ли сыграть», «стоимость», «легальные цели», «сколько тянуть» не зашиты в `if`: ядро строит предложенный результат, активные статические способности его правят.
8. **DSL эффектов.** Начинать с закрытого набора примитивов и селекторов, выращенного из 2–3 реальных механик (П34). Для уникальных карт — escape hatch на скрипте или в коде, как в LoR и GRE. Подсказки ИИ хранить рядом, как в Forge (`AIPriorityModifier`, `SacMe`).
9. **Выборы.** Каждая точка выбора — `DecisionRequest{player, kind, options, constraints}` в состоянии. Бот, тест и UI отвечают командой `Decide`.
10. **Скрытая информация.** Клиент получает `view(state, player)`, скрытые карты — без `def_id`. Перемешивание и броски RNG только на сервере. Серверный бот тоже получает только `view`, иначе он «читит» и искажает баланс.
11. **Детерминизм.** RNG только из состояния, упорядоченные коллекции вместо хеш-итерации, целые числа вместо float в правилах, без системного времени. Версия правил и контента пишется в реплей.
12. **Реплеи и тесты.** `seed + [Command]` и есть реплей. Каждый баг становится сценарием (П42), корпус реплеев с хешем итогового состояния гоняется в CI (П43), массовые бот-партии ловят паники и нарушения инвариантов (П45).
13. **Сеть.** Для пошаговой ККИ — авторитарный сервер и запрос-ответ. Мгновенный отклик дают локальной анимацией намерения до подтверждения.
14. **Undo** для пазлов, обучения и hot-seat: персистентное состояние или журнал команд с пересимуляцией от seed. В PvP undo по правилам обычно запрещён.

### 4.3 Порядок внедрения для малой команды

1. `rules-core`: команды, чистый `apply`, сериализация, seed. Сразу headless-тест «маленькая партия».
2. Очередь действий и простые триггеры. Вместо слоёв — аддитивные модификаторы.
3. Клиент проигрывает события, UI отвечает на `DecisionRequest`.
4. Данные карт в таблицах или JSON со схемой и валидатором, горячая перезагрузка данных.
5. Случайный бот (фаззинг) → жадный → ISMCTS.
6. Реплеи как регрессия, телеметрия для баланса.
7. Авторитарный сервер с фильтром видимости, когда понадобится PvP.
8. Конвейер замен, слои и whiteboard — когда появятся карты, которым они реально нужны.

Открытые движки для чтения: phase-rs и argentum-engine (функциональное ядро), Forge (карты текстовыми скриптами, ИИ), XMage (карта как класс, тесты), Fireplace (самый наглядный DSL), SabberStone (onion-модель). Код под AGPL (SabberStone, Fireplace, Spellsource) можно читать, но нельзя заимствовать в закрытый проект.

## 5. Игровой ИИ для ботов-плейтестеров

Боты на [этапе 7](pipeline.md#этап-7-измерительный-стенд) — измерительный прибор, а не противник для игрока. Один бот меряет свою стратегию, а не игру, поэтому нужны несколько стилей. Все боты работают через тот же интерфейс, что и игрок: получают `view` и `DecisionRequest`, отвечают `Command`. Методы автоматического плейтеста и метрики — в [playtesting-metrics.md](playtesting-metrics.md).

| Бот | Как устроить | Что даёт | Источник |
| --- | --- | --- | --- |
| Случайный | Равномерный выбор из законных команд, включая ответы на `DecisionRequest`. Лимит шагов на партию, проверка инвариантов после каждой команды | Фаззинг правил: паники, зависания, незаконные состояния. Нижняя граница: если он часто побеждает умного, решения мало значат | Синтез; Schwab 2014 |
| Жадный | Оценка каждой законной команды на шаг вперёд функцией позиции (здоровье, стол, рука, ресурс). Веса — в данных, чтобы менять без кода | Базовый баланс, очевидно сильные карты | Mark & Dill 2010 (utility-оценка) |
| Стилевой эвристический | Тот же жадный с весами под стиль: агро ценит урон по герою, контроль — размен и карты | Матрица матчапов по архетипам | Graham, Dill, Lewis (Game AI Pro) |
| ISMCTS | На каждой итерации детерминизация скрытого из `view` бота, поиск по информационным множествам, бюджет по времени или итерациям, rollout-политика с подсказками из данных карт | Баланс при сильной игре, доминирующие стратегии | Cowling, Powley, Whitehouse 2012; Sturtevant (GAP2); Roelofs (GAP3) |
| Ограниченный | Любой из ботов с фильтром законных команд: механика X запрещена | Важность механики: насколько падает доля побед без неё | Пайплайн, этап 7 |

**ISMCTS и ККИ.** Обычный MCTS с полным состоянием видит руку соперника и даёт завышенную силу. ISMCTS строит дерево по информационным множествам и борется со strategy fusion. Главные грабли в ККИ — большой фактор ветвления и составные ходы (Roelofs, GAP3). Составной ход удобно дробить на цепочку атомарных решений через `DecisionRequest`: дерево растёт глубже, но уже (синтез). MCTS требует тысяч дешёвых копий состояния, поэтому до него нужен чистый редьюсер (П21). Модуль `gym` в argentum-engine — пример отдельного входа для MCTS и self-play.

**Скорость симулятора.** Ориентир — Hearthstone: лёгкий ИИ прогонял «nearly nine to eleven thousand games» на одно серверное ядро (Schwab, GDC 2014). Число партий на замер считается по точности (`sample_size.py` в пайплайне), и десять колод по 2401 партии — уже 24 тысячи партий, поэтому скорость симулятора прямо ограничивает замер. Что держать в горячем пути:

- ядро без движка, логов и анимаций; поток событий для клиента можно отключать;
- дешёвое копирование состояния: персистентные структуры или явный компактный clone;
- генерация законных ходов, `apply` и ход бота покрыты бенчмарками по пайплайну скилла для языка проекта;
- параллелизм по seed: партии независимы, каждое ядро играет свой диапазон seed;
- одинаковые seed и версии ботов дают одинаковый JSONL (иначе сравнение до и после бессмысленно).

**Боты для реального времени.** Для агентов в экшене и стратегиях подходят BT (П37), utility (П38), GOAP и HTN (П39) с blackboard (П41). В пошаговых ККИ они нужны реже: там выигрывают оценка позиции и поиск. Автотесты самого ИИ: Skarupke, «Automated AI Testing» (Game AI Pro Online 2021).

## 6. Чеклист ревью кода игры

Игровые пункты для [этапа 9](pipeline.md#этап-9-ревью-кода-и-дизайна) поверх стандартного ревью языка проекта. Нарушение пунктов 1–8 — баг, он возвращается на этап 6 с тестом. Ревью дизайна — по [design-review.md](design-review.md).

| # | Пункт | Как проверить |
| --- | --- | --- |
| 1 | Ядро правил собирается и тестируется без движка, сети и IO | Тесты правил запускаются отдельной командой без редактора; в модуле правил нет импортов движка |
| 2 | Состояние меняют только команды через один `apply` | Поиск записи в состояние из UI, анимаций и обработчиков ввода |
| 3 | Детерминизм: один RNG в состоянии, seed записан; нет системного времени, float в правилах, итерации хеш-коллекций с недетерминированным порядком | Два прогона симулятора с одним seed дают побайтно одинаковый JSONL и хеш состояния |
| 4 | Нет скрытого глобального состояния: синглтонов, статических полей, Service Locator для RNG и состояния | Поиск глобальных и статических изменяемых данных; две партии в одном процессе не влияют друг на друга |
| 5 | Порядок разрешения задан явной структурой (очередь, стек, фазы); триггеры одного события упорядочены детерминированно | Сценарий с несколькими триггерами на одно событие даёт порядок из спецификации |
| 6 | Эффекты взаимодействуют по спецификации: на каждое взаимодействие из спеки есть сценарный тест; замены отделены от триггеров; SBA после разрешения, а не внутри | Сверить примеры «дано / когда / тогда» спецификации со списком сценарных тестов |
| 7 | В ядре нет логики конкретных карт (`if card.id == ...`) | Поиск id и имён карт в модуле правил |
| 8 | Производные характеристики вычисляются, ауры и баффы не мутируют базу | Тест: наложить и снять ауру в разном порядке — итог совпадает |
| 9 | Каждый выбор игрока — `DecisionRequest`; бот, тест и UI отвечают одной командой | В логике нет ожидания UI и колбэков интерфейса |
| 10 | Данные валидируются схемой в CI: типы, обязательные поля, ссылки между таблицами | Сломанная ссылка в данных роняет сборку, а не партию |
| 11 | Клиент и бот получают только `view`; RNG и перемешивание только на авторитетной стороне | Тест: `view` соперника не содержит `def_id` карт в руке и колоде |
| 12 | Реплей (seed + команды + версия правил и контента) воспроизводит партию | Корпус реплеев в CI сверяет хеш итогового состояния |
| 13 | Каждый исправленный баг правил получил сценарный тест | Сверить список исправлений с новыми тестами |
| 14 | Случайный бот играет тысячи партий без паник, зависаний и нарушений инвариантов | Прогон на стенде этапа 7, ноль ошибок |
| 15 | Сейвы и реплеи содержат `schema_version`, есть миграции и тест на старом «золотом» файле; горячие пути покрыты бенчмарками | Тест загрузки старого файла; отчёт бенчмарков до и после правки |

## 8. Расхождения и пробелы

**Расхождения**

- **Sea of Thieves.** Доклад GDC 2019 об автотестах геймплея читал Robert Masella. Jessica Baker выступала с другим докладом на Unreal Fest Europe 2019. Доклад про Minecraft — Henry Golding, GDC 2021.
- **Game Engine Architecture.** 4-е издание вышло в апреле 2026 двумя томами (CRC Press / Taylor & Francis); 3-е издание 2018 года [устарело].
- **MTG Arena GRE.** Анонс 2017 года называл движок «machine learning» — это маркетинг, [устарело] как техническое описание. Верить тексту Werner 2023: C++ + CLIPS, парсер GRP.
- **1500 Archers.** gamedeveloper.com указывает автором Paul Bettner, классически статью цитируют как Terrano & Bettner (GDC 2001).
- **Dungeon Siege.** В слайдах Bilas «более 7300» типов объектов; пересказы с 73 000 — вероятная опечатка.
- **Halo 2.** Официальное название доклада Isla — «Handling Complexity in the Halo 2 AI» (встречается и «Managing Complexity»).
- **Hearthstone.** Официального доклада Blizzard о движке правил нет. Advanced rulebook и модель тегов — реверс-инжиниринг сообщества: использовать как проверенный образец дизайна, а не как «так сделано в коде Blizzard».
- **Лицензии.** Forge — GPL-3.0; XMage, GGPO, flecs, EnTT — MIT; phase-rs и GGRS — MIT/Apache-2.0; Tracy — BSD-3-Clause; SabberStone, Fireplace — AGPL-3.0; Spellsource — AGPL-3.0, кроме модуля `spellsource-game` под GPL-2.0. Лицензия argentum-engine не определена.
- **Spellsource.** Ранее указанный репозиторий `carlhu/Spellsource-Server` — устаревший форк (2018); живой проект — `hiddenswitch/Spellsource`.
- **Scott Bilas.** Оригинальные PDF на scottbilas.com больше не открываются (редирект на 404); пользоваться копией.

**Пробелы**

- Доклада GDC или поста крупной студии о версионировании сохранений не найдено. П31 опирается на официальную документацию Factorio (миграции) и Unreal (`FCustomVersion`), плюс Fowler.
- Нет игрового первоисточника по property-based тестам геймплея. П45 опирается на документацию Hypothesis и proptest; нашлись только любительские движки (например, фаззинг ходов на Hypothesis в хобби-ККИ).
- Конвейер Google Sheets: один подробный пост студии (Hallett, Hutch, 2021) и инструменты (Beamable Game Content Designer, импортёры для Unity). Доклада GDC нет.
- MCTS конкретно для Hearthstone или MTG: академические работы есть, но не проверены.
- Overwatch: аннотация доклада Ford проверена (ECS + детерминизм), а командные кадры 16 мс и прочие детали — только из вторичных разборов (например, блог Edgegap); видео не просмотрено.
- Hearthstone: тезис «сервер считает, клиент проигрывает изменения тегов» первоисточником не подтверждён; HearthSim описывает только свой протокол Kettle, «смоделированный по» настоящему.
- Посты Bitsquid blog о hot reload не открылись (таймаут); принцип подтверждён слайдами Persson, GDC 2011.
- П28: перемешивание id скрытых карт при уходе в скрытую зону — общая практика без проверенного источника.
